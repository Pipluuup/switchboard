# 02 · 架构与技术决策

## 技术选型与理由

| 选择 | 理由 |
|---|---|
| FastAPI + uvicorn | 单文件可运行、异步流式转发顺手、自带 OpenAPI |
| SQLite（WAL） | 零部署；WAL 支持交接期新旧进程同时写 |
| JSON 配置（`data/config.json`） | 人可读、可备份、可手工编辑；pydantic 模型校验 |
| React + AntD + Vite 前端 | 控制台要管 9 个视图、表格列宽/筛选/多态表单，原生 JS 撑不住；Vite 构建产物直接落到 `web/`，后端与 PyInstaller 都只认 `web/` 这一个目录 |
| pywebview（桌面壳） | Web 与桌面两种形态共用同一套后端 + 前端，只多一层原生窗口壳，不存在两套逻辑 |
| PyInstaller（可选） | `scripts/build_exe.py` 打包单 exe，"拷贝即用" |

> 前端在 2026-10 迁到 React。旧版原生 HTML/JS 的实现已删除
> （Git 历史里仍可追溯，commit `6f2d59d` 之前）——**现在只改 `frontend/src/`**。

## 两条请求链路

**管理面**：浏览器 → `/`（`web/` 静态产物）→ `fetch /api/*` → `admin_routes.py` →
`config.py` / `database.py`。鉴权：设置管理口令后要求 `X-Admin-Token` 头。

**代理面**：Claude Code → `POST /v1/messages`（或 `/v1/chat/completions`、`/v1/responses`）→

1. 客户端 Key 鉴权（`config.py` 存储的 Key 表，`sk-px-` 前缀约定）
2. `limiter.py` 限流检查（RPM / 每日 Token）
3. `config.py` 映射解析：请求模型名 → 别名匹配 → 得到目标模型与（可选）绑定上游
4. `upstream_pool.py` 选上游：按请求模型过滤 `models` 白名单 → priority/weight 排序
5. 协议转换（按「入站协议 × 上游协议」查表，见 [03](03-PRD-代理核心与上游调度.md)）
6. `caveman.py` 压缩（若启用；见 [01](01-产品总览与路线.md) 的 Token 优化）
7. 转发（流式则 SSE 透传转换）、失败计数/冷却/熔断、
   按 `max_retries` 与故障转移链（`plan_chain`）依次尝试下一档（5xx/429/404/网络错误切档）
8. `database.py` 落日志（模型、Token、延迟、成败、上游、压缩统计）

## 协议与转换层

三套协议：Anthropic Messages、OpenAI Chat Completions、OpenAI Responses。

- 入站路由：`/v1/messages`、`/v1/chat/completions`、`/v1/responses`
- 上游协议：`Upstream.protocol` = `anthropic` | `openai` | `responses`
- 转换按 `(入站协议, 上游协议)` 查表，**请求与响应各一张表**
  （`proxy_routes.py` 的 `_REQUEST_CONVERTERS` / `_RESPONSE_CONVERTERS`）

> `responses` 与 `chat` 共用一套语义（Responses 只是形状不同），所以同一对方向
> 复用同一个转换函数。`config.py` 的 `Protocol` 字面量里如果出现没有实现的取值，
> `endpoint()` 会静默走 `else` 分支打到 `/chat/completions`——
> `test_frontend_contract.py` 专门盯着这个，防止又加一个没实现的协议。

## 数据模型（`data/config.json`）

| 实体 | 关键字段 |
|---|---|
| Settings | host, port, admin_token, log_retention_days, enable_log, request_timeout, cooldown_seconds, failure_threshold, health_check_interval, health_check_enabled, auto_open_browser, use_system_proxy, caveman_*（Token 优化）, voice_mode / voice_auto_min_tokens / voice_auto_min_messages / voice_ignore_cache（Say less 三态）, circuit_*（熔断器，见下） |
| Upstream | id, name, base_url, api_key, protocol(`anthropic`\|`openai`\|`responses`), enabled, priority, weight, timeout, max_retries, models[], note, key_url（运行态字段 healthy/cooldown_until/… 由 `runtime_state()` 追加，不落盘） |
| ModelMapping | id, alias, target, upstream_id, chain: list[ChainHop]（故障转移链，空=退化老语义单档）, enabled, note；`hops()` 负责退化，详见 [03](03-PRD-代理核心与上游调度.md) 第 1 节 |
| ClientKey | id, name, key, enabled, rate_limit_rpm, daily_token_limit, allowed_models[], upstream_id, note |
| ClientProfile | id, name, client(claude/codex/gemini), client_key_id, model, enabled |

请求日志在 `data/proxy.db`（SQLite WAL：`proxy.db-wal/-shm`），仅元数据，按
`log_retention_days`（0=永久）清理。

同库还有一张 **`usage_daily_rollups`** 日聚合表：把明细按「天 × 上游 × 实际模型」
压成一行，**不受保留期影响**。窗口长于保留期时（默认 30d > 7d）用量统计改查它，
这样 30 天窗口不会被日志清理截断。写入走「按日期删除后重算」，幂等。
详见 [04](04-PRD-用量统计.md)。

## 配置生效语义

| 改动 | 生效方式 |
|---|---|
| 上游/映射/Key 增删改 | 保存即生效（下次请求读取） |
| 除 host/port 外的 Settings | 保存即生效 |
| **host / port** | 只能走 `POST /api/server/restart` 交接，见 [06](06-PRD-监听地址热更新.md) |
| 配置导入 | 覆盖上游/映射/Key；**不含** host/port 与 admin_token |
| **旧版 `voice_enabled`（布尔）** | 启动时一次性迁移成 `voice_mode`：`true→on`、`false→off`，并落盘 |

## Say less 三态与自适应判定

Say less 往 system 注入电报体规则（先结论后解释、砍客套话）。它有个内在矛盾：
**改写 system 就等于改写可缓存前缀**——缓存命中价一丢，可能比省下的输出 token 还贵。
所以它不是开关，而是三态（`Settings.voice_mode`）：

| 模式 | 行为 |
|---|---|
| `off`（未启动） | 永不注入 |
| `on`（启动） | 总是注入（不管缓存） |
| `auto`（自适应，默认） | 按这次请求的实际情况判定 |

`auto` 的判定顺序（`caveman.voice_decision()`）：

1. 上游支持 prompt cache 且用户没勾「缓存优先也注入」→ **跳过**
2. 会话消息数 < `voice_auto_min_messages`（默认 4）**且**
   输入 token < `voice_auto_min_tokens`（默认 2000）→ **跳过**（满足任一即注入）
3. 其余 → **注入**

判定结果（模式 / 原因 / 本次消息数与输入 token）随 `caveman_stats` 一起进请求日志，
「优化」列展示——用户能直接看到这次为什么注入、为什么没注入，不用猜。

> **压缩收益与规则开销分开记**：注入规则会让请求变大（约 +1900 字符）。
> 若拿注入后的体积算「节省率」会得出 -1234% 这种荒唐数字，所以
> `caveman_stats` 里 `saved_pct` 按「压缩后、注入前」的体积算，
> 规则开销单独记在 `voice_added_chars`。

## 熔断器

上游异常时自动拉黑一段时间，而不是让每个请求都去撞一次。三态状态机
（closed / open / half_open），参数与错误分类见
[03](03-PRD-代理核心与上游调度.md)。

两个关键设计：

- **错误率判定 + 最小样本数**——抖动型上游（失败/成功交替）因为每次成功
  都会清零「连续失败」计数而永远打不中阈值；改看窗口内错误率，
  但样本不足时（`circuit_min_requests`）不判定，避免冷启动节点被误杀；
- **错误按状态码分类**——客户端自己的 400/404/422 不算上游的失败，
  401/403 立即拉黑。

## 前端构建

- 源码在 `frontend/src/`，构建产物输出到 `web/`（`vite.config.ts` 的 `outDir: '../web'`）

### 前端契约测试守什么

旧版这个测试查的是 `web/app.js` 的 DOM id，前端迁到 React 后 `web/app.js` 不存在，
它长期在 `FileNotFoundError` 里形同虚设。现在改为查真正的契约面：

1. **API 路径对齐** — 前端调用的 `/api/*` 必须在 `admin_routes.py` 注册过
2. **后端可达性** — 后端注册的管理面路径必须至少被前端用一次（抓死接口）
3. **协议枚举一致** — 前端下拉选项 = 后端 `endpoint()` 实际支持的协议；
   `config.py` 的 `Protocol` 字面量每个取值都必须有实现
4. **视图 ↔ 路由对齐** — ViewKey ↔ 菜单项 ↔ 组件文件 ↔ 渲染语句四者对齐

> 它已经抓到过真问题：`/api/caveman/preview` 后端实现了但前端从不调用（死接口），
> 以及前端 `Upstream.protocol` 类型漏了 `'responses'`。

- 本机注意：机器全局 `HTTP_PROXY=127.0.0.1:58889`，一切访问本机的 HTTP 客户端必须
  绕过代理（httpx 用 `trust_env=False`，urllib 用 `ProxyHandler({})`）
